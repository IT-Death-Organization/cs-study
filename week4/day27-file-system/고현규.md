# 1. 파일 시스템의 역할은 무엇인가?

> 파일 시스템(File System)은 보조 기억 장치(디스크 등)에 저장된 데이터를 파일과 디렉토리 단위로 관리하고, 사용자나 프로그램이 이름으로 접근할 수 있게 해주는 운영체제의 구성 요소입니다.

물리적인 디스크에는 파일이라는 개념이 없는 row한 데이터만 존재합니다. 파일 시스템은 이 raw 데이터를 논리적인 파일과 디렉토리 구조로 추상화합니다.

### 주요 역할

1. **데이터의 논리적 추상화**
    * 사용자는 파일 이름(경로)만으로 데이터에 접근합니다. 실제 데이터가 디스크의 어느 블록에 있는지는 파일 시스템이 관리합니다.
2. **저장 공간 관리**
    * 빈 블록 할당, 삭제된 파일의 공간 회수, 단편화 완화 등으로 디스크 공간을 효율적으로 사용하게 합니다.
3. **메타데이터 관리**
    * 파일 크기, 생성·수정 시간, 소유자, 권한 등의 정보를 유지하고, 이를 통해 보안과 접근 제어를 지원합니다.
4. **일관성 및 복구**
    * 정전이나 오류 시에도 데이터 일관성을 유지하거나 복구할 수 있도록 저널링 등의 기법을 제공합니다.

<br>

파일 시스템은 복잡한 하드웨어(HDD or SSD or Cloud Storage)가 어떻게 되어있든 사용자에겐 open, read, write로 똑같이 접근하고 제어할 수 있게 해줍니다. 이러한 관점에서 파일 시스템은 "인터페이스"라고 할 수 있습니다.

<br>

# 2. 파일 할당 방법(연속, 연결, 인덱스)의 차이와 장단점은?

| 방식 | 저장 방식 | 장점 | 단점 |
| :--- | :--- | :--- | :--- |
| **연속 할당** | 파일을 디스크상 **연속된 블록**에 저장 | 순차 접근이 빠름, 구현 단순 | 외부 단편화, 파일 확장 어려움 |
| **연결 할당** | 블록마다 **다음 블록 번호**를 저장해 연결 리스트처럼 연결 | 외부 단편화 없음, 확장 쉬움 | 순차 접근만 유리, 중간 블록 직접 접근 느림 |
| **인덱스 할당** | 파일별 **인덱스 블록**에 해당 파일의 블록 번호들을 모아 둠 | 임의 접근 가능, 확장 가능 | 인덱스 블록 공간 필요, 작은 파일도 인덱스 1블록 사용 |

### 1) 연속 할당 (Contiguous Allocation)

파일을 디스크에서 연속된 블록들에 차례대로 저장합니다. 시작 블록 번호와 길이만 알면 해당 파일의 모든 블록을 바로 계산할 수 있어 순차 접근이 매우 빠릅니다. 대신 디스크에 조각난 빈 공간(외부 단편화)이 생기고, 파일 크기가 커지면 뒤에 다른 파일이 있을 경우 파일 자리를 옮겨야 하는 번거로움이 생깁니다.

### 2) 연결 할당 (Linked Allocation)

각 블록 안에 "다음 블록 번호"를 저장해 연결 리스트처럼 이어 붙입니다. 파일이 여러 조각으로 나뉘어 있어도 되므로 외부 단편화가 해결되고, 파일 크기가 늘어날 경우 끝에 블록만 추가하면 되어 확장이 쉽습니다. 반면 N번째 블록을 찾으려면 처음부터 따라가야 해서 임의 접근이 느리고, 포인터를 저장하는 공간이 블록마다 필요합니다.

### 3) 인덱스 할당 (Indexed Allocation)

연결 할당에서 각 블록들이 가지고있던 포인터를 따로 빼서 관리하는 느낌입니다. 파일마다 인덱스 블록을 두고, 그 블록에 "이 파일이 사용하는 데이터 블록 번호들"을 배열처럼 모아 둡니다. 따라서 특정 위치(오프셋)의 데이터가 어느 블록에 있는지 계산해서 바로 접근할 수 있어 임의 접근이 가능합니다. 대신 작은 파일이라도 인덱스용 블록을 하나 쓰게 되고, 매우 큰 파일은 인덱스가 여러 블록이 될 수 있어 다단계 인덱스 등이 필요합니다.

# 3. inode란 무엇이며 어떤 정보를 저장하는가?

> inode(Index Node)는 파일 하나당 하나씩 존재하는 메타데이터 구조체로, 파일의 데이터 내용은 담지 않고 속성과 데이터 블록 위치만 저장합니다.

리눅스 계열 파일 시스템에서 파일들의 신분증 혹은 명세서 역할을 합니다.

### inode에 저장되는 정보

1. **파일 종류 및 권한**
    * 일반 파일, 디렉토리, 심볼릭 링크 등 파일 타입과 읽기/쓰기/실행 권한
2. **소유자 및 그룹**
    * UID, GID (사용자 ID, 그룹 ID)
3. **크기 및 타임스탬프**
    * 파일 크기(바이트), 최종 수정 시간(mtime), 최종 접근 시간(atime), 메타데이터 변경 시간(ctime) 등
4. **데이터 블록 위치**
    * 실제 데이터가 저장된 디스크 블록 번호들. 직접 블록 포인터, 간접/이중 간접/삼중 간접 블록 포인터로 큰 파일도 지원
5. **링크 수**
    * 이 inode를 가리키는 디렉토리 엔트리(하드 링크) 개수

참고로 "inode 번호"로 파일을 식별하며, 디렉토리는 "파일 이름 → inode 번호" 매핑 테이블이라고 보면 됩니다.

<br>

# 4. 디렉토리는 어떻게 구현되는가?

> 디렉토리는 파일 이름과 inode 번호(또는 해당 메타데이터 위치)의 매핑을 담는 파일입니다. 사용자가 경로로 파일을 찾을 때 이 매핑을 따라갑니다.

### 구현 방식

### 선형 리스트
디렉토리 엔트리를 [파일명, inode 번호] 쌍의 리스트로 저장합니다. 구현이 단순하지만, 특정 이름을 찾을 때 선형 탐색이 필요해 $O(n)$입니다. 파일 개수가 많으면 느려집니다.

### 해시 테이블
파일 이름을 해시해서 버킷에 저장합니다. 평균 $O(1)$에 이름으로 inode를 찾을 수 있어 대규모 디렉토리에 유리합니다. 충돌은 체이닝 등으로 처리합니다.

<br>

디렉토리 자체도 inode를 가지며, 그 inode가 가리키는 데이터 블록에 "자식 파일/디렉토리 이름 → inode 번호" 목록이 들어 있습니다. 루트(/)의 inode 번호는 고정되어 있어 경로 탐색이 여기서 시작됩니다.

<br>

# 5. 디스크 스케줄링 알고리즘(FCFS, SSTF, SCAN, C-SCAN)은?

> 디스크 헤드는 그 이동거리를 줄일수록 성능이 좋아집니다. 따라서 디스크 스케줄링 알고리즘을 사용하여 헤드가 이동하는 시간(탐색 시간)을 최소화 하는것이 목표입니다.

### 1) FCFS (First-Come First-Served)

요청이 도착한 순서대로 처리합니다. 단순하고 공정하지만 헤드가 요청 간에 양끝을 왔다 갔다 하며 이동할 수 있어, 탐색 시간이 길어질 수 있습니다. 스케줄링 오버헤드는 없습니다.

### 2) SSTF (Shortest Seek Time First)

현재 헤드 위치에서 가장 가까운 트랙에 있는 요청을 다음에 처리합니다. 평균 탐색 시간은 줄어들지만, 먼 트랙의 요청은 계속 밀려나 기아(Starvation) 가 발생할 수 있습니다.

### 3) SCAN (엘리베이터 알고리즘)

헤드가 엘리베이터 처럼 한쪽 끝에서 반대쪽 끝으로 쭉 이동하면서 그 방향에 있는 요청을 모두 처리하고, 끝에 도달하면 다시 반대로 스캔합니다. SSTF의 기아 문제를 해결할 수 있습니다. 하지만 중간부분에 위치한 요청들이 더 자주 서비스 받는 불균등이 있습니다.

### 4) C-SCAN (Circular SCAN)

SCAN과 비슷하지만, 끝에 도착하면 다시 처음으로 돌아가 다시 합니다. 반대 방향 요청의 대기 시간이 더 균등해질 수 있어, SCAN보다 대기 시간이 더 균등합니다. 다만, 다시 시작지점으로 돌아갈 때 시간이 걸립니다.

| 알고리즘 | 특징 | 단점 |
| :--- | :--- | :--- |
| **FCFS** | 순서대로, 공정함 | 탐색 비효율, 성능 변동 큼 |
| **SSTF** | 탐색 시간 감소 | 기아 가능 |
| **SCAN** | 균형 잡힌 성능, 기아 완화 | 끝까지 가야 방향 전환 |
| **C-SCAN** | 응답 시간 균일 | 한 방향만 서비스, 끝에서 점프 |

# 6. 저널링 파일 시스템은 왜 필요하며 어떻게 동작하는가?

> 저널링(Journaling)은 데이터 변경 내용을 먼저 로그(저널)에 기록하고 나중에 실제 디스크 구조를 갱신하는 방식입니다. 시스템이 갑자기 꺼졌을 때 파일 다 날아가는 불안감을 해결해줍니다.

### 왜 필요한가?

파일을 수정할 때는 "블록 할당", "inode 갱신", "디렉토리 엔트리 갱신" 등 여러 디스크 쓰기가 순서대로 일어나야 합니다. 이 도중에 정전이 나면 일부만 쓰여져 파일 시스템 구조가 깨진 상태가 될 수 있습니다. 예전에는 전체 디스크를 검사하는 fsck로 복구했는데, 디스크가 커질수록 시간이 오래 걸립니다. 저널링은 "어떤 작업을 하기로 했는지"를 먼저 로그에 남겨 두므로, 복구 시 그 로그만 보면 됩니다.

### 동작 방식 (일단 적어두고 나중에 실행)

1. **저널에 기록 (Log)**
    * 수행할 작업을 저널 영역에 트랜잭션 단위로 기록함
2. **실제 파일 시스템에 반영 (Commit)**
    * 저널에 쓴 내용을 실제 inode, 비트맵, 디렉토리 등에 적용합니다. 이게 완료되면 이제 갑자기 꺼져도 복구가 가능합니다.
3. **저널 정리 (Checkpoint)**
    * 2번에서 저장한 내용들을 실제 파일 시스템에 물리적으로 저장합니다. 그 후 로그를 지웁니다.
